    カメレオンナイト
    システム解説ガイド

    床の圧力マットで動く「カメレオン役」と、スマホのライトで敵を照らす「灯り役(最大7人)」が協力して、夜の森から脱出するゲームです。このガイドは、仕組みをテーマごとに分け、工夫した点と難しかったこと(原因と対策)まで説明できるようにまとめたものです。

    0主要C#コードの行数
    0マップ(A・B・C)
    0敵の種類(見た目はMeshy AI製の7体)
    0同時に遊べる灯り役
    0ESP32コントローラー方式

    30秒で説明するなら

    Unity製の協力型ゲームです。カメレオン役は、ESP32につないだ圧力マットを踏んで移動し、止まると擬態して無敵になります。灯り役は、画面のQRコードをスマホで読み取るだけで参加し、指や傾きでライトを動かして敵を照らして倒します。光の球を2つ集めて門から脱出するまでの時間と撃破数がスコアになり、マップごとのランキング(Excelで管理できるCSV)に残ります。

    01

    全体の構成何が、どこから、どこへ流れているか

    ゲーム本体はUnity(6000.4.3f1、Built-in レンダーパイプライン)のWindowsアプリです。入力は2系統あり、カメレオン役はESP32→UDP/USB、灯り役はスマホのブラウザ→HTTP/HTTPSでPCに届きます。PCの中では NightGame が司令塔になり、地形・敵・ギミック・画面・音・ランキングを順番に動かします。

    工夫シーンを「コード」で組み立てる

    Unityのシーンは手作業で配置せず、エディタ用スクリプト NightSceneBuilder が毎回ゼロから組み立てます。カメラ、月明かり、各サーバー、敵モデルの参照まで、すべてコードで決まります。

    • だれがビルドしても同じシーンになる(再現性)。
    • シーンファイルの衝突で作業が壊れにくい。
    • 地形はゲーム開始時にマップごとに生成するので、シーンには「部品」だけを置く。

    工夫Unityエディタを開かずに作って試す

    ビルドは -batchmode -nographics のコマンドで行い、出来上がったexeを自動撮影モード(-nightAutoShot)で起動します。タイトル→プレイ→敵に照射→ランタン→結果画面まで、14枚前後のスクリーンショットを自動で撮って確認しました。

    難しかった画面を見ずに「見た目」を保証する

    発光やちらつきの不具合は、ログの数値が正しくても画面では違うことがありました。そのため、必ず実際のexeで撮影した画像で確認する流れにしています(詳しくは「光と発光」「ビルドとテスト」)。

    02

    ゲームの流れ(状態遷移)画面はどう切り替わるか

    NightGame は5つの状態を持ち、状態ごとに受け付けるキーと描く画面が変わります。exeを起動するとまずマップ(コース)選択から始まり、ゲーム開始前に名前を入力します。

    キー操作まとめ

    画面キー動き
    タイトル123 / Enterマップ選択 / 名前入力へ
    名前入力Enter / Esc開始 / マップ選択へ戻る
    プレイ中WASD・矢印 / Esc移動 / 一時停止
    一時停止Esc / T再開 / ステージ選択へ
    結果R / Tやり直す / ステージ選択へ

    工夫シーンを読み直しても「戻り先」を覚える

    やり直しやステージ選択は、シーンを丸ごと読み直して初期化します。読み直すと普通の変数は消えるので、static の「タイトルへ戻る」フラグだけを残し、次の起動処理で名前入力を飛ばすかどうかを判断しています。

    難しかった要望の変化に合わせた起動の仕方

    最初は「exeですぐゲーム画面へ」でしたが、ランキングをマップ別にしたことで「起動はマップ選択から、開始前に名前」へ変わりました。今は起動オプション -skipTitle を付けたときだけ選択を飛ばせます。

    03

    マップと地形通路グラフ・メッシュ生成・描画の不具合対策

    マップは「通路(線分)」と「広場(円)」の組み合わせで定義されています(NightMap)。この同じデータから、見た目の地面メッシュ・当たり判定・敵の経路探索をすべて作るので、見た目と動きがずれません。

    仕組み3つのマップ

    A 森の迷路
    分岐が多い。導きの花・祠
    B 遺跡攻略
    階段・高台・石造遺跡(高低差あり)
    C 中央湖の周回
    湖のまわりを周回。橋と小島

    同じマップは毎回同じ景色になるよう、マップIDから決まる乱数(線形合同法)で木や岩を配置しています。

    仕組み同じデータを使い回す関数

    • SurfaceAt(x,z) … その場所の地面の高さ
    • Walkable(x,z) … 歩ける場所か
    • ConstrainActor … 通路の外に出たら内側へ戻す
    • ClearSight(a,b) … 2点の間が見通せるか
    • NavigationPath … 通路グラフ上のダイクストラ法で経路

    工夫邪魔な木を自動で隠す

    カメラはプレイヤーの斜め後ろから見下ろすため、手前の木の葉がプレイヤーを隠してしまいます。プレイヤーの前方にある木の葉だけを毎フレーム非表示にする処理(UpdateCanopies)を入れました。

    難しかったこと:地面の「線」「ちかちか」「ガビガビ」

    地面の描画不具合は4回、それぞれ別の原因でした。見た目は似ていても原因が違うため、1つずつ切り分けています。

    1地面に線がたくさん出る

    症状通路に細い線が多数
    原因帯メッシュを作る処理で、三角形を作る順番が頂点の追加と混ざり、裏返った三角形ができていた
    対策頂点をすべて追加してから、別のループで三角形を作るように修正

    2通路がちらつく(Zファイティング)

    症状重なった面がちらちら入れ替わる
    原因カメラの手前クリップが0.1で、奥行きの精度が無駄に近くへ使われていた
    対策カメラは常に約17.7離れているので、手前クリップを3に上げて精度を必要な範囲に集中

    3ギザギザの細い線がちかちか

    症状オレンジ色のギザギザ線
    原因光の道の葉っぱが地面ぎりぎり(0.06上)に置かれ、場所によって地面に埋まって端だけ見えていた
    対策葉を0.22浮かせ、照準リングなども0.15上へ。修正後に拡大画像で確認

    4曲がり角のちかちか・地面のガビガビ

    症状角でちらつき、地面が粗い
    原因隣の通路の帯がまったく同じ高さで重なっていた。テクスチャは細かく高コントラストの斑点
    対策通路ごとに2mm刻みで高さをずらす。斑点を2回ぼかし、異方性フィルタ8・MSAA 4倍
    深掘り:なぜ手前クリップを上げるとちらつきが減るのか

    深度バッファの精度は、カメラに近いほど細かく、遠いほど粗くなります(おおよそ距離の2乗に比例して粗くなる)。手前クリップが0.1だと、精度のほとんどが0.1〜数mの範囲に使われ、実際に地面がある約17m先では粗くなります。手前を3にすると、同じビット数でも17m付近の分解能が大きく上がります。それでも「完全に同じ高さ」の面は区別できないので、4つ目の対策(2mmずらし)が別に必要でした。

    04

    カメレオン(プレイヤー)と擬態止まると無敵、という駆け引き

    カメレオン役は上下左右に動くだけで、攻撃はできません。攻撃は灯り役の光が担当します。その代わり、止まると擬態してゲージがある間は無敵になり、擬態に入った瞬間に周りの敵を押し返します。

    数値擬態ゲージ

    擬態に入る
    0.3秒止まる(ゲージ30以上)
    減る速さ
    40 / 秒(擬態中)
    回復
    22 / 秒(移動中)
    切れたあと
    35まで回復するまで使えない
    押し返し
    半径5m、速さ11(近いほど強い)
    HP
    100

    工夫周りの色に溶け込む

    擬態中は、近くにある木・岩・地面の色(NearestTerrainColor)にカメレオンの色を寄せます。見た目でも「隠れている」ことが分かります。

    難しかったMeshy AIのモデルを動かす

    本体と歩きアニメが別ファイルで出力されるため、SetupChameleonModel で骨格(アバター)を共有させ、歩きをループ再生(1.4倍速)にしています。さらに、歩きアニメだけ腰の高さが約0.2高く焼き込まれていて、歩き出すと浮いて見えたため、アニメのカーブを静止姿勢の高さに合わせて補正しました。

    05

    圧力マット入力(ESP32)Wi-FiでもUSBでも、WASDと同時でも動く

    床の4枚の圧力センサーを ESP32 が読み取り、「前・後・左・右」を踏んでいるかをPCへ送ります。受け取るのは PressureMatServer です。キーボードのWASDと常に合成(OR)しているので、開発中も展示中も同じビルドで動きます。

    方式1Wi-Fi(UDP)

    esp32/pressure_mat。50msごとに "1,0,0,1" のような文字をUDPでPCの5005番ポートへ送ります。

    方式2USBシリアル

    esp32/controller。踏み状態が変わった瞬間と200msごとに、1バイト(0xA0+ビット)を送ります。例: 0xA9 = 前+右。COMポートは自動で探し、抜き差しされても探し直します。

    工夫2つの形式を取り違えない

    1バイト形式は上位4ビットが必ず 1010 です。文字形式の '0' '1' ',' 改行 は上位4ビットが 1010 にならないので、混ざって届いても区別できます(ControllerStreamParser)。

    数値判定の猶予

    入力が切れたとみなす
    500ms 受信なし
    「接続中」表示
    2,000ms 以内に受信(チラつき防止)
    USB探索
    開いて4秒待つ / 2秒ごとに探し直す
    ESP32と判定
    正しい形式を3回受信

    難しかった押しても反応しない

    症状マットを踏んでも動かない
    原因PCのWi-Fiが変わり、IPが 10.101.141.82 → 192.168.43.204 に変化。ESP32は古いIPへ送っていた
    対策HUDに「コントローラー: 接続中(USB/Wi-Fi)」を常時表示。IPに左右されないUSB方式も用意

    工夫実機なしでテスト

    自動テストでは、ゲーム自身が自分宛て(127.0.0.1:5005)に "1,0,0,0" を1秒送り、キー入力なしでプレイヤーが前に進むか、送るのをやめて0.7秒後に「入力なし」に戻るかを確かめています。

    06

    スマホ連携(灯り役)アプリ不要・QRを読むだけで最大7人

    PCの中に小さなWebサーバー(PointerServer)を立て、スマホのブラウザに操作用ページを配ります。スマホは指の位置(または傾き)を毎秒20回 POST /pointer で送ります。名前の入力は不要で、ページを開いた瞬間に色が割り当てられます。

    工夫管理者権限なしで動くサーバー

    Windowsの HttpListener は管理者権限やURL予約が必要なことがあります。そこで生の TcpListener でHTTPを自前で読み書きしています。展示用PCで設定なしに動かすためです。

    工夫傾き操作のためのHTTPS

    iPhoneは、傾きセンサーの許可(DeviceOrientationEvent.requestPermission)をHTTPSのページでしか出しません。HTTP(8787)とHTTPS(8788)を両方立て、自己署名の証明書はWindowsのPowerShell(New-SelfSignedCertificate)で作ります。Unityの実行環境では証明書の作成機能が使えなかったためです。

    仕組み人ごとの色と人数

    • ページを開くたびに一意のIDを作り、サーバーが参加順に8色から割り当てる。
    • 自分の色をスマホ画面に丸で表示。ゲーム画面にも色の丸と「接続中 N/7人」。
    • 8人目は「満員です(最大7人)」と表示。抜けて10秒で枠が空く。

    難しかったこと:ライトの遅延

    症状スマホを動かしてからライトが動くまで遅い
    原因送信のたびに接続を閉じていた(Connection: close)。毎秒20回、TCPの接続(HTTPSならTLSの暗号化の握手も)をやり直していた
    対策同じ接続を使い回す Keep-Alive に変更。小さいパケットを溜めない NoDelay も有効に

    さらにAndroidは、画面が消えるとWi-Fiが省電力になり、送信が数百ms単位で遅れることがあります。ページ側で Screen Wake Lock を取り、画面を点けたままにしました。スマホのテザリングを使うと、複数台接続で遅延がぶれやすいことも分かったので、展示では普通のWi-Fiルーターを推奨しています。

    工夫指を止めても光が消えない

    スマホは触っていない間も0.25秒ごとに最後の状態を送り続けます(心拍)。指を止めると送信が止まって光が消える問題と、「接続中」が数えられない問題を同時に解決しました。

    難しかったQRにアクセスできない

    QRの中身は https://(PCのIP):8788/ です。Wi-Fiが変わるとIPが変わり、印刷したQRは使えなくなります。起動時に毎回IPを調べ、タイトル画面の左下にも表示。make_qr.bat で今のIPの印刷用QRを作れるようにしました。

    運用ファイアウォール

    同じWi-Fiの別端末から入れるよう、受信の許可が必要です。

    New-NetFirewallRule -DisplayName "ChameleonNight Unity" -Direction Inbound -Protocol TCP -LocalPort 8787,8788 -Action Allow
New-NetFirewallRule -DisplayName "ChameleonNight UDP" -Direction Inbound -Protocol UDP -LocalPort 5005 -Action Allow
    深掘り:傾き操作は「レーザーポインター」のように動く

    傾き操作は、スマホの上端を懐中電灯の先と考えます。最初の姿勢(または「中心をリセット」)を真ん中とし、上下は前後の傾き(beta)、左右は水平に回す角度(alpha)で決めます。角度をそのまま比例させず tan() で変換しているので、中心付近はゆっくり、外側ほど速く動き、実際に光線を壁に当てているような感覚になります。alphaは0°と360°の境目で値が飛ぶため、差を必ず −180〜180° に直してから使っています。

    07

    光と当たり判定・発光いちばん苦労したテーマ

    灯り役の光は、スマホが指した画面上の位置からカメラの光線を飛ばし、地形に当たった点を「照らしている場所」にします(NightFlashlight)。接続中の人数ぶん、スポットライトと照準リングが同時に出ます。

    試してみる:人数と光の大きさ

    人数が増えるほど1人分の光は小さくなります(平方根で緩やかに)。

    光の半径
    3.00 m

    半径 = 3.0 × max(1.1/3.0, 1/√人数)

    仕組み敵へのダメージ

    • どれか1つの光の半径内で、高さの差が1.8未満なら当たり。
    • 当たっている間、敵ごとの「光HP」が減り、0で倒れる。外れると回復する。
    • 約12秒ごとの閃光(雷)で、半径26mの敵全員にダメージ。1.3秒前に雷鳴で予告。
    • 以前はプレイヤーのすぐ近くに光が効かない「死角」があったが、重なった敵を倒せないため廃止。

    難しかったこと:「光が当たったら光る」が画面に出ない

    Unityの「発光(Emission)」を使って、当たった物を黄色く光らせようとしました。しかし、ビルドしたexeでは何をしても画面が変わりませんでした。

    1. 1. 発光色を専用の方法(MaterialPropertyBlock)で設定 → なぜか水色に。マテリアルを直接書き換えても同じ。
    2. 2. 木や岩のモデルに発光の設定(キーワード)が無いことを発見 → 発光できるマテリアルに差し替え。それでも変わらない。
    3. 3. カメラが別の場所を映している可能性 → カメラと照準を毎フレーム強制的に対象へ向けるテストを作成。
    4. 4. ありえない色(マゼンタ)を発光に入れても白いまま → 発光そのものが描画されていないと確定。敵が光って見えていたのは、元の色がたまたまオレンジ系だっただけだった。
    5. 5. ビルドに含めるシェーダーの設定漏れも直したが、それでも描画されず。
    6. 6. 発光をやめ、確実に描画される通常の色(_Color)を直接黄色へ近づける方式に変更 → 解決。
    学び:ログの数値(色の値)が正しくても、画面に出ているとは限らない。「ありえない色を入れて変化を見る」ように、結果がはっきり分かる実験で切り分けるのが近道でした。

    工夫テクスチャ付きモデルも光らせる

    Meshyの敵はテクスチャ付きなので、色を黄色にしてもテクスチャの暗い部分は暗いままです。そこで「1を超える色(×2.4)」を掛けて、暗い部分まで明るく光らせています。

    工夫当たっていることが分かる演出

    • 敵:赤く点滅+赤い火花。足元の赤い輪は、普段は毎秒5回、倒れる直前(光HP 30%未満)は太く毎秒16回点滅。
    • 花・ランタン・光の球:光が当たっている間、色付きの火花。
    • 木・岩:黄色(1, 0.92, 0.45)へなめらかに変化。

    判断試して外した演出

    「ダメージ中に敵が小刻みに震える」演出も実装しましたが、見え方の好みで外しました。モックアップで先に見てもらい、実装後も好みに合わせて取捨選択しています。

    08

    敵(AIと3Dモデル)通路に沿って追いかけ、角で詰まらない

    種類見た目(Meshy AI)速さ光HP接触ダメージ/秒特徴出現率
    群れ型月光の狼(四足)・紫の猪3.53411速くて弱い。3体でかたまって出る38%
    硬い型狼男のお化け・赤い熊のお化け・鎧のお化け2.0511524高さ約4.5。通路をふさぐ大きさ25%
    遠距離型狐火の狐1.86089m以内で見通せると立ち止まり、2.5秒ごとに弾を撃つ25%
    すり抜け型ミントの妖精2.620(一番低い)10通路を無視して木や崖をすり抜け、まっすぐ追ってくる。倒しても回復オーブを落とさない。暗い森でも見えるよう緑に光る12%

    光HPは表の値に全体の倍率0.6とマップ別の倍率がかかります。見た目は種類ごとに順番に使うので、同じ種類でも違うお化けが出てきます。

    出現はプレイヤーから12〜24m離れた通路上。間隔は最初2.4秒で、時間とともに最短0.7秒まで短くなります(門が開いた後はさらに15%速く)。同時に出るのは最大44体です。

    追いかけ方(3段構え)

    1見通せるなら直進

    ClearSight でプレイヤーまでの間が歩ける場所だけなら、まっすぐ向かいます。

    2見通せないなら通路グラフ

    カーブや分岐の向こうにいるときは、ダイクストラ法で求めた経路の中継点をたどります。経路は0.4秒ごとに引き直します。

    3壁に当たったら滑る

    進みたい方向が通路の外なら、0°→±20°→±40°→±65°→±90°→±125°と少しずつ曲げて、歩ける方向を探します。それでも0.3秒進めなければ、0.8秒だけ直進をやめて経路に従います。

    例外すり抜け型だけは通路を無視

    すり抜け型(PhaseTowardPlayer)は上の3段構えを使わず、プレイヤーへ一直線に進みます。通路の内側へ戻す処理(ConstrainActor)もかけず、高さだけ近くの地面へなめらかに合わせます(FollowGround)。近道できる分、速さは群れ型より遅い2.6にしています。

    難しかった近くの敵が角でスタックする

    症状最短ルートで向かってくる敵が角で止まる
    原因まっすぐ進もうとして通路の外にはみ出し、「内側へ戻す」処理で元の位置に押し戻され続けていた
    対策はみ出す前に、通れる方向へ曲げて壁沿いに滑らせる(上の3)。詰まり検出で経路に切り替え

    3Dモデルの取り込み

    難しかった骨もアニメもないモデル

    Meshy AIの「動物×お化け」7体は、骨もアニメもないメッシュだけでした。Blender 5.2を画面なしで動かす blender/enemies/rig_enemy_ghosts.py で、骨8本を自動で置き、頂点の重みを体の高さ・前後・左右の位置から計算して付け、ループするアニメ(Walk)を作ってFBXにしています。

    工夫お化けと四足で動きを分ける

    浮くお化け(熊・狼男・騎士・狐・妖精)は、ふわふわ上下に揺れ、しっぽがうねり、腕や翼・狐火が動きます。四足(狼・猪)は対角の脚を交互に出して歩きます。お化けは地面から少し浮かせて表示します。

    工夫軽くして大きさをそろえる

    元は4.5万〜20万面と重いので5000〜8000面に減らし、テクスチャも1024pxにしました。読み込んだ後に見た目の高さを測り、目標の高さ(群れ型1.4〜1.5・硬い型4.4〜4.6・遠距離型2.6・すり抜け型2.1)に自動で拡大縮小します。PlayableGraph で歩きクリップを直接ループ再生します。

    想定される質問と答え発表・展示で聞かれそうなこと

    スマホにアプリを入れる必要はありますか?
    いりません。PCが小さなWebサーバーになり、QRを読むとブラウザで操作ページが開きます。名前の入力も不要です。
    何人まで遊べますか?
    カメレオン役1人と、灯り役が最大7人です。人数が多いほど1人分の光は小さくなり、難しさのバランスを保ちます。
    なぜHTTPSも使っているのですか?
    iPhoneは、傾きセンサーの使用許可をHTTPSのページでしか出さないためです。タッチ操作だけならHTTPでも動きます。自己署名の証明書なので、スマホに警告が出たら「続行」を選びます。
    ライトが遅れるのはなぜ?
    以前は送信のたびに接続をやり直していたのが主因で、Keep-Aliveで解消しました。残る遅延は、Wi-Fiの混雑やスマホの省電力、テザリング経由の接続が主な原因です。展示では普通のWi-Fiルーターをおすすめします。
    Wi-Fiや会場が変わったら?
    PCのIPが変わるので、QRコードの中身も変わります。ゲームは起動のたびにIPを調べ直し、画面左下に表示します。印刷したQRは、make_qr.bat で作り直してください。
    敵が光っていたのに、なぜ「発光が効いていなかった」と分かったのですか?
    発光の色にマゼンタのような、ありえない色を入れても画面が変わらなかったからです。敵が光って見えたのは、もともとの色がオレンジ系だっただけでした。そこで発光をやめ、通常の色を直接変える方法にしました。
    ランキングを手で直したり消したりできますか?
    できます。exeと同じフォルダの ranking.csv をExcelで開いて、名前の修正や行の削除をして保存すれば、次にタイトル画面に戻ったときに反映されます。
    敵の3Dモデルはどう作りましたか?
    画像生成AIで作ったキャラ画像を Meshy AI で3D化・アニメーション付けしました。GLB形式のものはBlenderでFBXに変換し、Unity側では高さの自動調整とアニメのループ再生を自動化しています。
